# Guest checkout changes

Guests can continue buying without logging in. Checkout now validates delivery
details, fetches current dish and delivery prices on the server, and stores item
quantities and price snapshots. Existing product references are retained for
compatibility with older admin screens. New order details display snapshots;
historical orders fall back to their existing data.

## Payment and retry behavior

- The browser retains a checkout key across retries in the same tab. The server
  binds that key to the customer/session, delivery details, and cart quantities.
  Changed details require a new key, which the checkout page supplies automatically.
- A guest customer, pending order, and pending transaction are created atomically
  before requesting a payment URL. A database failure prevents initialization.
- Guests get a separate customer record per checkout, even when their email
  matches a registered account. Signed-in identity comes from the verified token.
- Retrying the same request reuses the saved order and payment reference. A
  revision-protected lease prevents simultaneous payment initialization.
- A gateway timeout never creates a new reference automatically. If initialization
  succeeded but its URL was lost, Paystack can reject a duplicate reference; the
  customer is directed to support rather than starting another payment. Support
  should check the existing reference before asking the customer to order again.
- The cart stays intact until successful verification. Only the matching cart in
  the originating tab is cleared; another cart created later is preserved.
- Both the return page and the signed webhook use the same finalizer. It verifies
  reference, amount in kobo, currency, and successful payment with Paystack. Order,
  transaction, and customer accounting updates commit together with a revision
  guard, so repeated or concurrent callbacks cannot count a purchase twice.
- Fulfillment status stays separate from payment status. An order being paid does
  not mean it has shipped or been delivered.

The existing 7.5% VAT and whole-naira total rounding policy are preserved. These
business rules were not changed or evaluated for tax compliance.

## Required deployment configuration

1. Set `SANITY_API_TOKEN` or the existing `NEXT_SANITY_API_TOKEN` to a server-only
   token with mutation access to the intended Sanity dataset. Both names are supported;
   `SANITY_API_TOKEN` takes precedence if both are populated. Keep project/dataset
   configuration consistent with the storefront. Neither token is sent to the browser.
2. Configure `NEXT_PRIVATE_PAYSTACK_SECRET_KEY`, `NEXT_PRIVATE_JWT_SECRET_KEY`,
   `NEXT_PRIVATE_EMAIL`, and `NEXT_PRIVATE_PASS`. Never commit their values.
3. Set `NEXT_PUBLIC_BASE_URL` to the site's HTTPS origin. This controls the explicit
   `/success` payment callback and emailed password links. Use a preview origin and
   test credentials for integration checks before production.
4. In the matching Paystack environment, set the webhook URL to
   `https://euodiawholefoods.com/api/paystack/webhook` for production (or the public
   preview URL plus `/api/paystack/webhook` for testing). The handler validates
   `x-paystack-signature` using the existing Paystack secret, then verifies the charge
   through Paystack's API. No additional webhook secret is required.
5. Studio/schema source is absent from this repository. If the company uses Sanity
   Studio, add the new `lineItems`, amount/currency, payment status, paid timestamp,
   checkout metadata, and hashed reset-token fields there. API writes are not
   validated against Studio schemas; the app provides its own validation.

## Guest accounts

After a guest purchase, **Set or reset password** sends an expiring link to the
email address. Signup explains this route rather than allowing someone to claim
guest purchases by choosing an arbitrary password. Only the emailed token enables
the selected guest account. Existing registered accounts take precedence over guest
records with the same email during password recovery, and login only selects
records with a password.

Tokens are stored as hashes, expire after an hour, and are consumed with a revision
guard. Password links generated by the old plaintext-token implementation must be
requested again after deployment. Multiple guest records are not merged into an
account automatically; historical associations require a separate verified process.

## Historical data and remaining work

- No existing customer/order documents are migrated or deleted. Older order totals
  may already include unpaid purchases; this change does not attempt an automatic
  repair. Legacy payment verification avoids incrementing those totals again.
- Older orders never stored purchased quantities or unit prices, so those values
  cannot be reconstructed reliably from this change.
- The earlier review's sensitive Sanity access, browser admin mutations, dependency,
  and statistics-query issues remain separate work. Private customer records must
  not be exposed through public dataset reads.

## Validation

`npm run test:checkout` runs isolated checks against the real checkout, payment,
account, webhook, and cart-session modules using mocked database/payment/email
dependencies. No remote mutations or real payments are made. CI runs these checks.

Before accepting live orders, use Paystack test mode to check a fresh guest purchase,
an existing-account email used as a guest, a cancelled payment and retry, repeated
webhook delivery, a closed-browser payment, and email activation followed by login.
Confirm the admin sees the correct purchased quantities and totals. A passing build
and mocked checks do not establish end-to-end payment or email delivery.

Implementation follows [Paystack webhooks](https://paystack.com/docs/payments/webhooks/),
[payment verification](https://paystack.com/docs/payments/verify-payments/), and
[Sanity transactions](https://www.sanity.io/docs/apis-and-sdks/js-client-transactions).


Validation completed: the company production build passed compilation, lint/type
checks, and generation of 45 pages. All 14 regression tests passed in both
worktrees. Five built public pages and 23 checkout JS/CSS assets returned HTTP 200;
malformed checkout/account requests and missing payment references returned HTTP 400.
Read-only Sanity checks accepted the new queries with nonexistent fixture IDs.
The existing statistics query still logs an undefined sum function during builds.
No real payments, emails, or database mutations were executed.

## Delivery price compatibility follow-up — October 20, 2026

Read-only inspection found 45 numeric dish prices and 100 delivery fees stored as
numeric strings. The original checkout guard incorrectly rejected the delivery
strings. Checkout now normalizes valid decimal text from server catalogue data,
while rejecting empty, negative, nonfinite, malformed, boolean, and unsafe values.
Admin delivery-fee create/update handlers normalize values before saving; the form
submits numeric fees. No existing catalogue documents were changed.

The regression suite now has 17 passing tests, including a 3000-naira meal plus
225-naira VAT and a text-stored 2500-naira delivery fee: total 5725 naira. All 45
published meal prices and 100 delivery fees passed read-only validation with the
updated parser. Invalid prices still fail before payment initialization or order
writes. The checkout summary also falls back to the meal title when name is absent.

## Checkout credentials and cart follow-up — October 20, 2026

The deployed Vercel variable was named NEXT_SANITY_API_TOKEN while the server read
SANITY_API_TOKEN, leaving checkout mutations unauthenticated. Both server-only names
are now accepted, with the canonical name taking precedence. Required configuration
is checked before order/payment writes. Failures distinguish storage and gateway
configuration/availability using response codes; logs contain only stage, service,
and HTTP status, not raw SDK request objects, secrets, or customer details.

The old browser cart-save effect and unused Sanity cart helper were removed.
Redux Persist already keeps the cart in browser session storage; no browser write
token is needed for cart changes. This removes the cart-save 403 without changing
checkout's server-side order persistence.

All 20 regression tests passed, including legacy token compatibility, browser-token
exclusion, missing configuration before writes, and credential-safe diagnostics.
The configured local Sanity token also passed a dry-run of the actual pending-order
mutation, with no documents persisted. The local Paystack credential was not rejected
on a read-only request for a nonexistent reference; no payment was initialized.
These local checks do not establish the permissions or validity of Vercel's key values.
